# vivo WATCH GT 真机故障分析及 0.6.33 修复记录

范围：390×450 方屏，BlueOS / BES2700IBP。依据用户提供的应用诊断 JSON、系统日志包和照片调查；本轮已获授权修改并发布。原始日志、照片、会话 ID、健康及设备个人数据不进入仓库。

官方视觉来源仍为 openGym 最新发布 **v1.4.5**，固定提交 `2d70e026effc6602f513555166a97443520f0572`。本次通过 GitHub latest API 再次核实。遵循上游 AGPL-3.0-or-later。用户最新明确要求取消音乐控制，因此本版本只保留概览 / 当前组 / 统计三个横向页面。

## 证据与归因边界

系统 `exception.log` 中包含多年的历史故障，不能全部归因于本应用。本次有明确对应的记录是 **2026-11-19 12:39:15.112**：`RunningApp: com.zcode.gymtimer`，`runningPage: /Workout`，`jsloop` 在申请 **61 bytes** 时断言失败。记录同时给出：

| 指标 | 日志值 |
|---|---:|
| JS 堆总量 | 2,234,676 bytes |
| JS 堆已用 | 2,230,328 bytes |
| 最大可分配空闲块 | 60 bytes |
| jsloop 最近 10 秒 CPU | 95.7% |

这是本次训练页的真实 JS 内存耗尽证据。单独改变动画、字体大小或触摸阈值不能消除对象保留问题。它不能证明所有历史死机都由同一原因引起。

所提供 heap snapshot 包含 82,006 个元素，其中有 51 个 `pendingEdits` 属性，位于多份不同修订的会话对象。BlueOS Studio framework `7af9d62` 的 `Vm` 同时证实：页面动态新增属性也通过响应式 `data` 写入；`staticData` 读取保持原始对象；`reactiveMap` / `targetMap` 在页面销毁时清理。快照不包含全部原生代理内部引用边，不能据此画出每份会话的完整保留路径。

用户照片显示历史摘要在右侧截断，底部箭头接近物理圆角。BlueOS 文档明确文本 `text-overflow` 默认 `clip`；上游 `Quiet` 使用 Ellipsis。另一个原生 render tree 的活动页为 Index，不能将其当作照片中 Workout 的几何测量。

应用诊断显示队列仍有待处理事件，旧训练回执与当前训练消息交错。诊断日志容量有界且有淘汰记录；未保留表冠事件不代表表冠没有转动，也不能证明其根因只是某个事件字段。

## 结构及更新链路

- `app.ux` 持有 App runtime、通信、持久化和训练心率订阅。
- `Index` 读取计划目录，开始或恢复训练后进入 `Workout`。
- `Workout` 中三个横页使用 `show` 保留有界原生子树；统计页内部仍按指标切换。
- 数值二次点按进入 `Keypad`，提交后回训练页；动作列表使用 `ExerciseList`；结束进入 `Summary`。
- 写入路径保持 `commitPageAction → commitSessionAction → writeStoredAtomic`，持久确认后发布显示变化及发送意图。
- 训练业务文档放入 `staticData.sessionModel.current`，不进入响应式代理；显示区域只订阅文本、标量及小型列表。
- HR 路径改为 `health.subscribeSample → loadState('hr') → addHr → App 聚合 → 按已有阈值 flushHr`。读操作不再复制整份 rows、syncBase、pendingEdits。
- 时钟仍按绝对时间计算；HR 显示每 2 秒、卡路里每 5 秒更新。区间列表按 key 复用原对象，而非每次采样替换整个数组。

## 音乐检索结论及最终处理

用户给出的 [audioManager 文档](https://blueos.niceshare.site/api/system/audiomanager/) 提供 music stream 的音量、静音等接口；[audioPlayer](https://blueos.niceshare.site/api/system/audio/) 和 [mediaManager](https://blueos.niceshare.site/api/system/media/) 提供本应用播放器，没有证实可控制其他应用或手机的媒体会话。上游 Wear OS 使用 Android 的 `dispatchMediaKeyEvent`、系统音量和 Media Controls Intent，不能直接移植为 BlueOS API。

用户随后明确要求砍掉音乐入口，最终发布物中**没有音乐页、音量接口声明或隐藏的第四横页**。

## 已完成验证及限制

新增回归读取真实 .ux 脚本，模拟 Studio 中已观察到的 Page 绑定、staticData 和强代理缓存契约。对旧源码运行时，会话代理累积、显示列表身份及包装表冠三项均失败；修复后通过。此模型不模拟 GPU、固件内存分配器和真实蓝牙时延。

另验证：200 次模拟滑动、每次 20 个 move 复用两个坐标对象；旧/新协议下连续完成 5+2 组及积压队列恢复；拒绝缺失、错误 sid、未应用的祖先；未选择字段的表冠事件不写训练存储；隐藏页面取消焦点任务。最终测试数量与构建结果见同版本发布说明。

BlueOS 编译器验证实际模板使用 `$show`，文本样式编译为 `textOverflow: ellipsis`，三页指示器、横滑边界一致，音乐和非上游概览入口不存在。签名检查验证证书身份、RSA、资源摘要及包版本，不以桌面截图代替编译检查。

## 真机复测方案

使用同一 WATCH GT、相同系统版本、亮度和连接条件，分别安装旧/新版本。每种场景至少重复 10 次，记录中位数、最慢值、失败次数；有界诊断中的丢弃计数一并记录。

| 项目 | 步骤及指标 | 获取限制 |
|---|---|---|
| 冷启动 | 完全退出后点击图标，外部视频测至首次可操作；10 次 | JS onInit 时间不等于完整进程启动耗时 |
| 页面切换 | 三页往返 200 次，录屏/外部视频测松指至稳定画面；统计失灵、误触和崩溃 | 桌面自动化耗时不能替代触摸或蓝河渲染耗时 |
| 重量/次数与表冠 | 选中各字段，各慢转/快转/反转 20 次；切页、熄屏、返回键盘后再测 | 核对 field_selected、crown_input、local_commit 记录；原始日志未覆盖全部表冠输入 |
| 长列表与长文案 | 20 个动作、多字中英文名称、40 行历史、五位数值；滑至列表首中尾 | 文本按官方行数省略是预期行为；检查半字硬裁断、数字和按钮缺损 |
| HR 与休息并行 | 10 分钟持续心率更新，含多次休息、评分和页面切换 | 没有可用帧时间 API 时报告观测停顿，不伪造 FPS |
| 连续组 | 手表完成至少 5+2 组，再测 50 组；核对手机完成数、游标、重量和休息 | 手机明确业务 committed 才算已保存，不能只看蓝牙 send success |
| 内存变化 | 相同页面在启动后、5/10/30 分钟采集系统 meminfo、heap snapshot、render tree | 采集有开销；系统总内存/其他应用节点不等于本应用 JS 堆；本地测试无法实测设备峰值 |
| 断连与失败 | 训练中断连，继续编辑/完成，恢复连接；旧关闭记录与新会话交错；确认新能力协商 | 未升级手机不能宣称新压缩协议已启用；不删除待传数据来获得“队列清零” |
| 30 分钟稳定性 | 混合心率、三页切换、完成组、休息及断连恢复，记录系统异常、内存曲线、最慢响应 | 本轮没有连接真实设备，尚无 30 分钟稳定性数据 |

## 分阶段后续工作

1. **本版**：修复有证据的状态代理、分配、刷新、事件依赖和裁切机制；取消音乐与多余概览入口，发布可复测包。
2. **真机验收**：重点复测左右滑动和重量/次数表冠，采集同条件内存及异常日志；据此确认剩余原生堆压力和焦点行为。
3. **官方完整状态迁移**：仍需完成 count-in、weigh-in、timed HoldView、已完成组 fix/save、warmup、side、superset 及完整 Pulse 曲线的端到端协议和 UI 对照。不得以删除这些官方功能冒充完整复刻，也不得把本次用户取消的音乐页重新加入。
