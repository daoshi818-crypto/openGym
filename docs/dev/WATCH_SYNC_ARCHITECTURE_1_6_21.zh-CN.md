# 手机—BlueOS 手表同步架构与传输量对照（1.6.21 / 0.6.24）

## 依据与边界

参考用户提供的《KeepStrong_Xunji_训练中同步逻辑详解.md》。Xunji 的 RN/native 命令名、部分 payload、结束记录分片和 ACK 有明确材料；KeepStrong Flutter 的通道和命令日志较明确，但许多业务字段、冲突算法来自逆向推断。本文不把参考文档的“建议通用流程”当作已证实的竞品实现，也不声称取得了竞品真实链路流量。

本项目与参考均借助 vivo 运动健康和 DeviceRpc 互通；并非 Flutter/React 页面自己建立 BLE 连接。此次沿用现有 SDK、连接入口和 UI 风格，重整业务交付顺序及数据传输。

## 各阶段动作怎样同步

| 阶段 | 参考方案的可见行为 | 本项目此前实现 | 本次实现与保留的原则 |
| --- | --- | --- | --- |
| 启动/恢复 | ready/context 后交付训练数据；Xunji 用 Train_Start 等命令 | 存在先发裸计划，再补完整当前状态的窗口 | 有训练 store 时先完成 hello 能力协商，手机 checkpoint 后原子交付完整当前训练：全部动作、各组真实值与完成态、焦点、休息、版本；匹配完整回执后才宣告已交付。旧协议保留兼容 |
| 修改重量/次数 | Change_Move_Data 定位 moveidx/setidx/type/data | 有 weight/reps 小事件，同时发送权威状态 | 保留逐字段事件及稳定目标 ID，权威状态在已确认基线上计算增量 |
| 完成/撤销一组 | On_Set_Done / on-done / on-un-done 等 | set/unset，事件持久化、依赖排序、手机落盘后确认 | 同样本地立即更新；组完成携带本组数值和休息意图。手机处理完成后精确确认该事件，并回传变动状态 |
| 切换动作/组 | 参考以动作、组下标定位；完整焦点规则并非都可见 | focus 事件及快照焦点 | 在同一训练内切动作发 focus，使用动作实例 ID、组 ID 与会话 ID，不重新发起训练。不等待手机 ACK 才切页。新会话隔离旧会话焦点 |
| 新增/删除组、动作结构变化 | Xunji 有复制/删除组命令 | 稳定 ID、结构版本及权威快照 | 保留精确业务事件；结构与基线不兼容时发送全量，不把下标错位当成另一个组 |
| 快速点击、暂时断开 | 参考有队列/恢复，具体业务承诺强度不完全明确 | durable pending events、依赖图及精确 ACK | 保留。每个真实业务事件独立保存/确认；可合并“待发权威状态”，不可合并或清掉尚未确认的业务操作 |
| 双端同时改同一字段 | 参考存在冲突提示/选择，不能认定竞品没有冲突 | 手机优先，但空闲清理也可能生成假手机版本 | 仅真实手机操作产生编辑版本；真正并发时自动采用手机，不显示冲突选择。版本检查继续防止旧事件覆盖新值 |
| 保存/放弃 | Xunji On_Finish 全记录分片及 On_Finish_Ack；KeepStrong 完整规则未知 | close journal、关闭 tombstone、历史保存决策 | 保存与放弃分别持久化交接，断连可重试。手机落盘后确认，重复关闭不产生重复记录；不以结束全量盲目覆盖手机 |

动作定义、各组数值和当前焦点是不同数据：首次交付包含完整动作清单和每组记录；训练中只传发生变化的事件/行/焦点；切动作不是再次发送整个计划。组下标同时存在以兼容旧协议，稳定 ID 才能保证重排、删组后不操作错对象。

## 本次确认的根因

1. 手机初始没有休息计时器时，清理逻辑也广播了新的“手机停止休息”版本。手表第一次完成组带来的休息意图因此被误判为旧操作，表现为第一次回退、第二次成功。现在只有真实计时器产生停止意图，并检查会话与来源；空闲清理不再制造手机编辑。
2. 裸计划只有处方摘要，并不包含当前组真实值、完成态和同步基线。先激活裸计划再补快照，会让首个操作发生在不完整上下文。现在使用握手后的完整原子启动；checkpoint 期间训练已更换则不能发旧训练。
3. 原始同步回执只按 sid 就可能触发“已确认”。现在须经传输层验证 transferId/sid/revision/hash；普通 v3 回执也检查快照 hash 与 commitRev。retained 表示保存了旧快照，不表示它成为可用增量基线。
4. 持久快照链路此前没有接入已有 diffWire，训练中重复发送完整动作与全部组。这是明确的额外负担，但并无真机证据证明它单独导致系统级黑屏。此次接入精确确认后的增量传输，并保留完整恢复源。

真实关闭路径新增 store/finish 集成回归：第一次落盘失败不得发 committed；恢复成功后再确认；手机重启重放同一关闭事件不得重复保存。保存和放弃均覆盖，未用 fake history push 替代真实 finish。

## 可靠增量的具体规则

- 首份数据无已确认基线，发送全量；新 sid、动作结构变化、增量不比全量小也发送全量。
- 只对精确匹配且 status=applied 的快照建立基线；retained、错误 hash 或未确认传输都不能成为基线。
- 同时至多一个在途快照和一个最新待发快照。在途传输不被每次点击取消；待发状态先保留全量，前一份 applied 后才针对准确基线生成增量。
- 增量包含变更的行、焦点、休息等字段；不重发未变化的动作定义。比较的是 UTF-8 字节数，不是字符串字符数。
- 增量的完整原始状态保存在手机持久传输记录内。进程重启继续重发相同字节；接收端报告基线缺口时，精确取消确认后使用完整源恢复。
- 快照任务的替换与业务事件 ACK 无关。不能通过清空事件队列、累计 ACK 或“2 秒内都算重复”来掩盖堵塞。
- 保留分片逐片确认、缺片恢复、校验和与 128 KiB 业务 JSON 上限。每片按至多 1000 个 UTF-16 代码单元切割并避免拆代理对，**不是每片 1000 字节**。
- 定时器在本地倒计时，传输状态变化和恢复信息；不是每秒重发所有训练记录。

## 数据量：可复现固定样本

运行：`node scripts/watch/measure-sync.mjs`。使用本项目真实计划/快照生成器、手表事件包装和持久分片协议，固定中文名称、稳定 ID、时间与一条已确认事件。无训练历史附加信息，无重试。真实训练名称、历史、ID 长度、待确认列表、重试次数都会改变结果。

单位均为 **UTF-8 业务 JSON 字节**；分片协议行计入 JSON 封装与传输回执，但不计 vivo SDK、编码、蓝牙链路等底层开销。下表不是整次点击的全部双向流量，更不是空中流量。

| 固定场景 | 2 动作 / 7 组 | 10 动作 / 50 组 | 20 动作 / 100 组 |
| --- | ---: | ---: | ---: |
| 首次完整训练快照 | 1,514 | 6,291 | 11,951 |
| 手表修改重量事件 | 453 | 453 | 453 |
| 手表完成一组事件，含休息 | 581 | 581 | 581 |
| 完成一组后的全量回传 | 1,677 | 6,454 | 12,114 |
| 相同变更的增量回传 | 523 | 523 | 523 |
| 全量回传的分片封装 + 回执合计 | 2,924 | 9,805 | 17,721 |
| 增量回传的分片封装 + 回执合计 | 1,333 | 1,333 | 1,333 |

两动作样本：单次权威状态正文减少约 69%，其传输协议总 JSON 减少约 54%；10 动作样本协议总 JSON 减少约 86%。这是同一项目全量/增量的受控比较，不代表与竞品相比的节省比例。更多已确认事件、评分或其他变化会让增量变大，不保证永远 523 字节。

参考文档的 Xunji 修改重量示例 `{command:Change_Move_Data,payload:{moveidx:2,setidx:1,data:80,type:weight},trainID:123456}` 按原文字符串字段序列化为 110 字节。我们的事件还包含事件唯一 ID、安装实例、会话/结构/基线版本、稳定目标 ID 和依赖。示例字段值也不同，不能把 110 对 453 当作实际总流量倍率。KeepStrong 的真实 schema 未完整取得，无法严谨给出其单包或完整训练总字节数。

## 局部界面边界

操作页与结束页补“放弃训练”，独立二次确认，明确不保存历史。结束页用原生列表容纳内容。状态与时钟共享有限宽度；重量/次数分别在受限容器内展示。保留已有样式、完成按钮与列表导航。组圆点是组选择器，已有 44px 点击区；动作通过标题/动作列表切换。

方屏与圆屏进行原生编译产物检查和浏览器语义预览。圆屏仅修必要的圆形安全边距、滚动可达性与长数值样式。浏览器预览不是 BlueOS 模拟器，不能证明物理手表的系统级死机已消失；最终仍须用“两动作五组+两组、快速完成/跳过、保存/放弃、关闭后开新训练”复测设备。
