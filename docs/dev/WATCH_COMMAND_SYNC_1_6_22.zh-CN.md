## 本次改变了什么

已有协议一直使用固定命令 `set/unset/weight/reps/rest/focus/pause/effort`，并不需要每次上传动作全集。此前成功后还会返回 `committed`，再另外启动一份权威状态传输；即使能传增量，仍有 begin、chunk、applied 等往返。第一组的重量/次数又是动作默认值来源，改变这些元数据时此前的保守差量算法会回退全量。

新链路在双方握手明确支持 `commandReceipts` 后使用：

```text
手表本地持久保存意图与 UI 状态
  → 固定命令（eventId + 稳定目标 + 冻结因果版本 + 发送时的已应用基线）
  → 手机串行决策，业务数据与精确确认一同 checkpoint
  → committed {eventId, status, commitRev, state: sync_delta}
  → 手表验证并原子落盘手机校正，移除对应本地覆盖，更新现有页面
  → 小型 sync_ack（sid + wireHash + commitRev + applied）
```

普通成功链路不再单独启动快照传输。`state` 是手机实际生成的权威差量，包含变化行、焦点/休息/暂停等变化字段，必要时带单个动作的默认重量/次数；不会为这些默认值变化重发整个动作列表。首次启动、增删组等结构变化、未知基线、超限或校验失败继续走完整可靠传输。

### 两个版本不能混用

- `baseCommitRev`：操作产生时的因果基线，参与字段冲突与依赖检查，写入意图后保持不变。
- `appliedHash/appliedRev`：真正发包时手表已经持久应用的手机快照，单独附在发送副本上，供手机选择差量编码基线。它不改变 eventId，不改变原始因果意图，也不能当成业务已确认。

这样前一条确认刚到、后一条命令已排队时，后者能利用当前真实基线，而不会通过改写因果版本掩盖冲突。独立命令确实同时在途时仍可能共享旧编码基线；校正无法应用就请求最新手机状态，不猜测、强行套用或回滚。

### 去重、重试与手机优先

- 手机将完整 `committed.state` 和业务决定一起持久化。相同 sid/eventId 再来时重放原决定，不从较新的手机状态重新生成另一份差量；休息、保存等副作用不重做。
- 手表收到确认后，先保存精确决定和校正状态，再出队。存储失败保留待重试事件；SDK 发送成功只表示传输成功。
- 差量以保存的手机 `syncBase` 展开，不能以手表乐观 UI 状态展开。确认历史只携带本次事件 ID；已提交覆盖仍按已应用权威 revision 安全移除。
- 手机真正同时改同一字段时自动保留手机值，手表应用校正；独立字段继续合并。内部仍保留原因和诊断记录，界面不要求用户选边。
- 晚到的旧快照回执不能覆盖较新的同会话同步基线。恢复请求优先从手机当前训练生成完整快照，修复只通过持久传输发送时历史缓存不完整的问题。
- App 的第一组默认值变化会再次触发计划 effect。只在命令校正与决定成功落盘后，用完全相同的计划字段覆盖这次自动推送；不提前抑制，不把 SDK 成功当应用确认。手机真正改动作/计划仍发送，显式“继续到手表”仍要求新的精确回执。独立覆盖 effect 先于及晚于 checkpoint 两种时序。
- 手机编码缓存最多 16 份、合计 512 KiB，仅作优化。缓存丢失/淘汰不影响业务去重与确认，只回退可靠同步。
- 差量正文最多 4,500B，整个确认最多 6,000B（UTF-8 JSON）；超限保留分片回传。手机先验证差量能准确重建 checksum；可选字段/顺序等无法重建时回退。
- 旧 v2、未声明能力的 v3、关闭保存/放弃流程都保留原有兼容及持久保障。本次没有改 UI，已有放弃按钮与确认仍在。

## 数据量：测量完整一次操作的业务往返

复现：仓库根目录运行 `node scripts/watch/measure-sync.mjs`。脚本使用实际事件包装、手机持久协调器、差量生成器和持久传输协议，测量该协调链路；另用 App 相同调用方式的集成回归验证页面计划 effect 不会额外回传状态。脚本本身不启动 React 页面。固定中文动作名、稳定 ID、时间与初始数据，无 Last time 历史与丢包重试。下表包含命令、业务确认、状态传输与其回执，**仅 UTF-8 业务 JSON，不是 SDK 或无线链路字节数**。

| 固定场景 | 改前完成+休息 | 改后完成+休息 | 改前修改重量 | 改后修改重量 |
| --- | ---: | ---: | ---: | ---: |
| 2 动作 / 7 组 | 3,599B / 9 条 | 1,599B / 3 条 | 3,347B / 9 条 | 1,292B / 3 条 |
| 10 动作 / 50 组 | 10,480B / 19 条 | 1,599B / 3 条 | 10,228B / 19 条 | 1,292B / 3 条 |
| 20 动作 / 100 组 | 18,396B / 29 条 | 1,599B / 3 条 | 18,144B / 29 条 | 1,292B / 3 条 |

两动作样本完成+休息约减少 56%，重量约减少 61%。这里选第一组，它影响动作默认字段，改前会回退全量；不表示旧链路每次都全量。只修改普通行且动作定义不变时，旧链路已有增量，节省幅度更小。改后命令增加了 40B 已应用基线证据：完成命令 581→621B，重量命令 453→493B；收益主要来自回程及省去单独传输。完成确认 879B，再加 99B 状态应用回执，总计 1,599B。

这些固定普通变更不随总动作数增长，并不承诺所有操作恒定大小：多个字段/动作同时变化、长名称/ID、结构改变、丢包重试都会改变体积。首次完整快照仍为 1,514 / 6,291 / 11,951B，不能省略动作名称、组信息等首次数据。

脚本保留上版全量/增量状态传输测量，与本版完整操作结果分开列出。参考资料的训记重量示例是 110B，尚未计入我方持久身份、因果依赖、稳定目标、确认等保障，不能直接用单条示例与整次往返比较。KeepStrong 未取得完整 schema，无法严谨给出总字节数。

回归覆盖实际手表页面/RPC 的五组加两组快速完成/跳过、手机并发改同字段与独立字段、确认丢失后重启精确重放、落盘失败重试、坏校验与同基线独立在途回执的安全恢复、重复旧回执、旧能力回退、传输预算与缓存淘汰。另执行完整前端测试、手机启动/文案检查、Android 和方/圆 BlueOS 原生构建。实际执行数量和结果记录在本版交付记录中。
